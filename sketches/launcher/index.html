The launcher, state by state

A box over the middle of the surface where any command the host defined can be found by name and run. Nothing here runs. It is drawn before it is built, so that it is argued about once.

A command is a name and a list of actions. Running it emits those actions, in order, exactly as if each had come from its own gesture. The launcher adds no way of doing anything; it is another way of asking for what the dock and the host can already do.

Open

#open

Centred across the surface, a fifth of the way down, 520px wide. A fifth rather than a half because the list grows downward from the query, and a box that starts at the middle runs out of room halfway through it. Same card as a notification: --radius-lg, a firm border and a deeper shadow, because this one is in front of everything and has the keys.

The dock is not dimmed. A command acts on what is behind the launcher — the window it would close, the slot it would split — so what is behind stays readable. The shadow is enough to say which is in front.

Empty, it lists every command in the order the host defined them, the first one chosen, so Enter on an open launcher does something predictable. Eight rows show; past eight the list scrolls inside the card, and the card never grows past the surface.

Not decided: what opens it. A key, presumably, but the machine has no keys yet — drawn as the host sending open the launcher as an event, until the dock grows key bindings of its own.

Finding one

#find

Typing narrows the list to the commands whose name contains the letters typed, in order, not necessarily together: spr finds Split right. Letters that start a word rank first, so the obvious one is on top, and the matched letters are bold so it is plain why each row is there.

Nothing found

#none

A plain line where the list was, and the card shrinks to it. Enter does nothing and the launcher stays open, because the likeliest thing next is a deleted letter, not a second try from scratch.

Running one

#run

Enter, or a click on a row, runs the chosen command: the launcher closes and the command's actions come out of the next emit_actions, in the order it lists them. One batch, so a command that closes a window and focuses the next one is one change on screen and not two.

Not decided, on purpose: commands that ask for something before they run — Move window to… then a slot, Open… then a file. There is no general answer yet, and none will be guessed at; each one is decided when it is in front of us, and the board says no more about commands than it has to until then.

Closing

#close

Escape, or a press anywhere outside the card, closes it and emits nothing. The press outside is spent closing the launcher: it does not also pick up a tab or a gap, because a click meant to dismiss something should not move something else.

It opens empty every time. What was typed last time is gone, so the first key is always the start of a name.

Not decided: who owns the text being typed. The machine can hold the query and match it, but a caret, selection and an input method for non-Latin text are the platform's job, and nothing in the machine may name a browser type. Drawn as the runtime keeping the text field and sending the query as an event each time it changes.
